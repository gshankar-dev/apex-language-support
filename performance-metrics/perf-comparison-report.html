What Changed Between v0.5.0 and v0.5.39

Per the engineering team, three internal changes were made:

  1. Standard library classes are now loaded lazily. Previously, all standard Apex types (String, List, Map, etc.) were fully loaded from a protobuf archive at startup. Now they're loaded on demand when first referenced.
  2. More debouncing during symbol relationship building. The server now batches up more work before processing cross-file relationships.
  3. Cross-file reference tracking switched from a graph to map structures.

We also found a fourth change by diffing the server bundles:

  1. Workspace batch processing was restructured. In v0.5.0, each batch of files is unpacked and queued for processing as it arrives (one at a time, with gaps in between). In v0.5.39, batches are stored first, then all processed at once in a tight loop with no breathing room for other requests.

Why v0.5.39 Is Slower

The changes interact with each other in an unfortunate way during workspace loading:

  • Lazy loading + batch processing = a lot of extra work at the worst time. When the server compiles hundreds of files, each file references standard types. In v0.5.0 those types were already in memory. In v0.5.39, the first reference to each type triggers an on-demand load from the protobuf archive. This adds overhead to every single file compilation during the initial load.
  • Processing all batches at once removes the gaps that kept hovers responsive. In v0.5.0, each batch arrived from the client, got unpacked, and was queued individually. The round-trip time between batches gave the server a chance to handle hover requests. In v0.5.39, everything is queued in one shot, so the server grinds through all the work without ever pausing to respond to the user.
  • Larger debounce windows mean bigger bursts of relationship-building. With more work accumulated before firing, the server does more in each burst, which blocks the thread for longer stretches.
In short: v0.5.0 spreads the work out and stays responsive. v0.5.39 front-loads everything and locks up.

Suggestions

  1. Pre-load standard types before processing workspace batches. The lazy loading optimization makes sense for startup, but during a bulk workspace load the server knows it's about to compile hundreds of files. Hydrating the common standard types up front would avoid repeated on-demand loads during compilation.
  2. Go back to processing batches incrementally. The v0.5.0 approach of handling each batch as it arrives kept the server responsive. If the store-then-process-all approach is needed for other reasons, adding explicit yield points between batches would help.
  3. Use shorter debounce windows during workspace loading. Smaller bursts of relationship-building let hover requests get through in between.

Test Infrastructure

All tests were run using scripts/single-thread-bottleneck-test.js with the --server-path flag pointing at the installed extension server bundles. Each project size gets a fresh server process. Results are saved as JSON in performance-metrics/.

To reproduce:

# v0.5.0
node scripts/single-thread-bottleneck-test.js \
  --server-path ~/.cursor/extensions/salesforce.apex-language-server-extension-0.5.0/server.node.js \
  --label "release-0.5.0" --project large

# v0.5.39
node scripts/single-thread-bottleneck-test.js \
  --server-path ~/.cursor/extensions/salesforce.apex-language-server-extension-0.5.39-universal/dist/server.node.js \
  --label "pre-release-0.5.39" --project large
